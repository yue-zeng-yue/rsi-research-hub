## A dataset contract for self-improvement experiments

Before generation or training, assign each example a stable ID and a role: task generation, optimization, candidate selection, or final evaluation. Keep derivative data lineage: source ID, generator model, prompt version, verifier version, generation time, acceptance rule, and parent optimizer. If a model sees final-evaluation feedback, reclassify those examples as development data and obtain a new holdout.

Record whether feedback exposes only scalar success, intermediate verifier details, gold answers, complete solutions, or human critique. These access levels are different learning signals. For STaR-style rationalization, answer hints belong in generation and are removed from the final model input; for repository repair, gold patches should remain inaccessible during agent execution.

## Negative evidence and contamination controls

Store rejected generations, unsolved tasks, invalid tool calls, timeouts, and infrastructure errors as separate categories. Deduplicate semantically related tasks across train and final evaluation, not only byte-identical files. Use unseen repositories, catalog categories, tools, or task generators to support transfer claims. Public math and coding benchmarks can have unknown pretraining overlap; merely checking that a fine-tuning file omits test IDs does not eliminate that issue.

No new corpus, benchmark trajectories, paid API generations, or training data were created during this cataloging pass.
